# Источники публичного расписания Минска: проверка 16.11.2026

Ветка `codex/public-transport-signals`, этап 1 плана
[общественный транспорт и светофоры](../superpowers/plans/2026-11-16-public-transport-signals.md).
Проверка выполнена 16.11.2026 с машины разработчика; сеть работала. Результат
нормализации — [`import_schedule.py`](../../scripts/mobility/import_schedule.py),
отчёт покрытия — `data/processed/mobility/schedule.report.json` (локальный,
`data/processed/*` исключён из Git).

## Итог

1. **Технически** официальный раздел «Расписание городских и пригородных
   маршрутов» («Виртуальное табло», `/lookout_yard`) отдаёт JSON через
   внутренние XHR-эндпоинты. Они возвращают всё, что нужно расписанию: оба
   направления, остановки с ID и координатами, отправления по дням недели,
   полные времена **всех** остановок конкретного рейса и продолжение дня
   обслуживания после полуночи.
2. **Юридически** это не поддерживаемый публичный машинный интерфейс. Условия
   использования сервиса (ред. 01.10.2021) прямо запрещают автоматизированное
   извлечение, копирование, использование данных в работе иных программ и
   приложений и коммерческое использование. Официального GTFS, открытого
   набора и мобильного приложения у Минсктранса нет; по заявлению на его
   сайте, данные о расписании и движении предоставляются Яндекс.Картам и
   IBA (Transport BY) по партнёрским договорённостям.
3. **Статус зависимости: `unavailable`.** Для публикации расписания нужно
   письменное разрешение Минсктранса (API/GTFS/выгрузка) либо лицензированный
   фид партнёра. До этого транспорт «по расписанию» не считается готовым, а
   `schedule.json` содержит `status="unavailable"` и пустые `routes`/`calendars`.
   Сам нормализатор при этом рабочий: он проверен на синтетической фикстуре и на
   реальном частичном снимке bus 39 (локально, без публикации).

## Полнота данных (критерий этапа 1)

Проверено на выбранных коридорах `bus 39` и `tram 9` (см.
[corridors.json](../../scripts/mobility/corridors.json)) и контрольных маршрутах
`bus 100`, `tram 1`.

| Требование | Доступно | Комментарий |
|---|---|---|
| Оба направления | **Да** | `Route.Trips.StopsA` / `StopsB`, у каждого свой headSign (`EndStopA/B`). |
| Список остановок | **Да** | ID, имя, WGS84-координаты, `Bearing`, `StopState`; порядок задан направлением. |
| Рейсы | **Да** | Перечисляются отправлениями на остановке (`Schedule`), а полный состав рейса даёт `TripDepartures`. |
| Будни / выходные | **Частично** | Маски 31/96/127 существуют; у `bus 39` и `tram 9` на проверенных конечных **только 31 (будни)**. У `tram 1` — 31 и 96. Нужно подтверждение, что у 39/9 действительно нет выходного расписания, или поиск варианта/остановки с маской 96. |
| Период действия | **Нет** | Сайт не публикует ни начала, ни конца действия. Это обязательное поле `MobilityServiceCalendar`; даты должен подтвердить перевозчик. |
| Исключения по датам | **Частично** | `InfoExclusion` в формате «ДД.ММ.ГГГГ не работает» разбирается в `exceptions[]` (kind `remove`). `WorkingDay` (работа по расписанию другого дня) и `BadTimes` (отмена конкретных отправлений на дату) контрактом не выражаются. |
| Времена всех остановок | **Да** | `TripDepartures.model[]` — время каждой остановки рейса. Это `departure`; отдельных `arrival` и dwell нет, поэтому в контракте `arrivalS = departureS`, стоянка — модель экспортёра. |
| После полуночи | **Да** | Время продолжает счёт: 1458 мин → 87 480 с (> 86 400). Нужен fallback `dt+1440` при пустом ответе. |
| Варианты / укороченные рейсы | **Частично** | В интерфейсе есть `tripType` 0..3 и `OtherDirections`; контракт знает только `direction: 0\|1`. Парковые/укороченные рейсы не описываются одним вариантом — импортёр отбрасывает их с предупреждением. |

Модель межостановочного времени **не требуется**: источник публикует время каждой
остановки рейса. Модель нужна только для стоянки (dwell) и разгона/торможения —
это уже задача экспортёра и симуляции, а не импорта; времена остановок при этом
остаются исходными.

Фактические примеры (16.11.2026, локальные часы Минска):

| Маршрут | Направление | Остановок | Рейсов в будни (на конечной) | Пример рейса |
|---|---|---:|---:|---|
| bus 39 «ДС Восточная — Щедрина» | A | 15 | 10 | id 11420740: 15 остановок, 07:12–07:43 (432…463 мин) |
| bus 39 | B | 15 | 10 | — |
| tram 9 «ДС Серебрянка — Тракторный завод» | A | 12 | 27 | id 13954352: 12 остановок, 05:15–05:35 (315…335 мин) |
| tram 9 | B | 12 | 10 | Часть рейсов начинается не на конечной (парковые), поэтому конечная видит 10 из 27 прибытий. |

Это **не** полный снимок: сохранён один рейс на маршрут для проверки формата.
Полный снимок потребовал бы `Schedule` по всем остановкам и `TripDepartures` по
каждому отправлению; терминальная остановка не гарантирует перечисление
парковых рейсов, поэтому объединение по остановкам обязательно.

## Импортёр: границы и статусы

[`scripts/mobility/import_schedule.py`](../../scripts/mobility/import_schedule.py):

- `--from-raw <capture.json>` — офлайн-нормализация формата
  `minsktrans-board-capture@1` (снимок ответов `Route`, `Schedule`,
  `TripDepartures`). Без сети; результат детерминирован по входу.
- `--fetch-board --accept-source-terms` — исследовательский снимок с сайта
  (сеть только здесь, сессия+токен+браузерные заголовки, пауза между
  запросами). Требует явного согласия оператора; оригиналы ответов и
  `PROVENANCE.json` сохраняются в `data/raw/mobility/schedule/board-<дата>/`.
  Полный автоматический снимок в этой сессии не запускался: схема интерфейса
  проверена ручными запросами, а нормализатор — сохранёнными ответами. При
  первом запуске проверьте полноту: терминальная остановка не перечисляет
  парковые рейсы, начинающиеся в середине маршрута.
- Без аргументов — пустой `schedule.json` со `status="unavailable"` и отчётом
  с причиной.
- `--valid-from/--valid-to` обязательны, если есть рейсы: источник период не
  публикует, даты должны быть подтверждены официально.
- Синтетическая фикстура помечается `"synthetic": true`; без
  `--emit-unpublishable` её данные не попадают даже в
  `data/processed/mobility/schedule.json`, а статус — `synthetic`.

Проверки, которые выполняет нормализатор: неубывание времён, порядок `seq`,
существование остановок варианта, дубли ID рейсов/исключений, даты в периоде,
неизвестные остановки, рейсы без ответа `TripDepartures`, дубли календарей.
Проблемные рейсы **не исправляются** подстановкой интервалов: они
отбрасываются, а причины попадают в `warnings` и `report.checks` с счётчиками.

## Пробелы контракта (нужно решение lead)

1. `MobilityServiceCalendar` требует `startDate`/`endDate`, которых источник не
   публикует. Сейчас даты задаёт оператор; без них импорт завершается ошибкой.
2. Нет представления для «день работает по расписанию другого дня»
   (`WorkingDay`) и отмены отдельных отправлений на дату (`BadTimes`).
   `exceptions` умеют только `add`/`remove` целого дня.
3. `direction` — только 0|1, а у источника есть `tripType` 0..3 и
   `OtherDirections`; варианты маршрута в `schedule.json` отсутствуют.
4. Отдельного `arrival`/dwell у источника нет; контракт получает одно время на
   остановку. `complete=true` означает «все времена взяты из источника», а не
   «есть отдельные arrival/departure».
5. Для runtime-защиты `schedule.json` расширен полями `status` (и отчёт полем
   `publishable`). `export.py` обязан не публиковать данные при
   `status != "ready"`/`"partial"`; это нужно закрепить в контракте.
