## Шаг 0 — зафиксированная область

Область задана явным прямоугольником в локальных метрах (EPSG:32635 относительно
`PILOT_CENTER`), а не стороной квадрата:

| Параметр | Значение |
| --- | --- |
| Границы (локальные метры) | `minX=-11264`, `minY=-9216`, `maxX=12288`, `maxY=10240` |
| Размер | 23 552 × 19 456 м |
| Тайлы | 1024 м, индексы X −11…11, Y −9…9, **23 × 19 = 437** |
| Контракт в коде | `scripts/geo_config.py`: `CITY_BOUNDS_M`, `area_bounds_m()`, `tile_range()` |
| Halo извлечения | `CITY_HALO_M = 1000` м вокруг области |

Восточная граница расширена до **x = 12 288 м**, чтобы целиком взять аэродром
Липки (полосы до x ≈ 9 919 м, это ~1 км восточнее МКАД) и оставить после него
**≈ 2 369 м контекста**. Продуктовая цель — красивая и юзабельная карта, а не
минимально работающая: «работающий минимум» допускается только как подэтап.

Проверка по закреплённому PBF (`scripts/qa/b2_area_schema.py`, артефакты

## Шаг 0 — визуальный контракт

Сравнение идёт с референсом Warsaw izo по **пользовательскому результату**, а не
по исходным данным (у референса LoD2-здания GUGiK, NMT-рельеф и ортофото — это
отдельные пункты беклога, не B-2).

Контрольные территории (локальные метры, приблизительно ±0,5 км; уточняются на
первом LOD-срезе):

| Территория | Что проверяем | X, Y |
| --- | --- | --- |
| Центр (Октябрьская площадь / пр. Независимости) | регрессия уже принятого качества, landmarks | 0, 0 |
| Панельный микрорайон (Каменная Горка) | сохранность корпусов и дворов, LOD-переходы | −8 241, 4 593 |
| Восток (многоэтажный) | плотность, ночные окна, швы тайлов | 5 952, 2 922 |
| Частный сектор и зелёная зона (Лошица) | квартальная структура, растительность | −1 003, −6 261 |
| Промзона (МТЗ) | крупные объёмы, разрывы, крыши | 3 626, −1 439 |
| Развязка МКАД (север, пр. Независимости) | читаемость кольца и развязок, внешний контекст | 3 820, 6 463 |

Масштабы для review:

1. **Весь охват** — вся область 437 тайлов в допустимом LOD, без пустых полос.
2. **Район** — основной масштаб референса (~1,5–3 км по высоте кадра).
3. **Квартал** — полная геометрия, picking, переход детализации.

День и ночь — парные кадры для каждой территории; ночная читаемость (не средняя
яркость) и отсутствие «чёрных» дальних районов обязательны.

## Шаг 1 — контракт области и извлечение (ход работ)

Сделано в коде:

* `scripts/geo_config.py`: `CITY_BOUNDS_M`, `CITY_HALO_M`, `area_bounds_m()`,
  `tile_range()`, `tile_index_for_point()`; `CITY_SIZE_M` удалён,
  `area_bbox('city')` выводится из прямоугольника (оставлен как приблизительный
  ориентир).
* `scripts/geo_window.py`: точное UTM→WGS84 окно области + halo; общий модуль для
  извлечения и нормализации (никакого «метров на градус» в контракте).
* `scripts/ingest/extract.py`: точное WGS84-окно из прямоугольника + halo,
  проверка header bbox PBF, отбор way по bbox узлов вместо «первой вершины»,
  `feature_in_window` — пересечение bbox вместо «хотя бы одной вершины»
  (иначе терялись полигоны, накрывающие окно, и линии, пересекающие его без
  вершин внутри); в meta raw/trees записываются размер и **SHA-256** PBF.
* `scripts/normalize/normalize.py`: прямоугольная область вместо `half`,
  `tile_range()`, `areaBounds` в манифесте (`pilotBounds` оставлен как alias),
  `ground.clip` и coverage-отчёт по прямоугольнику; preflight пары raw/trees
  до тяжёлой обработки (area/epsg/center/окно с halo/размер и SHA-256 PBF),
  `--coverage-out` для staging; проверка `assigned_trees == len(trees)`.
  Назначение `building:part` переведено с O(части × здания) на STRtree-выборку
  кандидатов (правило «наименьший содержащий полигон» сохранено тестами);
  глобальный лимит деревьев для city поднят до 1 200 000, а `trees_budget_scale < 1`
  теперь **явная ошибка** (обход — `--allow-tree-thinning`), чтобы расширение
  площади не прореживало город молча; `--profile` печатает тайминги этапов и
  пиковый RSS (Windows `GetProcessMemoryInfo`).
* `scripts/normalize/trees.py`: `build_trees(..., bounds=...)`, обрезка рядов
  и отбор mapped-деревьев по прямоугольнику.
* Потребители coverage (`scripts/validation/coverage_report.py`,
  `scripts/qa/tree_coverage.py`) читают `boundsLocal`.
* Новые тесты: `scripts/normalize/tests/test_area_contract.py` (границы,
  437 тайлов, окно, enclosing-полигон, пересекающая линия, отброс далёких фич,
  владение краевыми точками, fail-closed preflight) и
  `scripts/normalize/tests/test_pipeline_guards.py` (правило родителя
  `building:part` и политика глобального бюджета деревьев).
  далёких фич).

Проверено:

| Проверка | Результат |
| --- | --- |
| `py_compile` изменённых скриптов | OK |
| Python unit suite (`pnpm run test:data`) | **152 теста OK** (было 114) |

`94 999` — это **raw building-feature** из извлечения (окно + 1 км halo), до
нормализации и дедупликации; напрямую с `31 783` нормализованными зданиями

Не сделано намеренно:

* полная нормализация 437 тайлов — по плану запрещено начинать тяжёлый прогон

* бинарный формат/Brotli, LOD обзора, бюджеты памяти — шаги 4–5 плана.

Первый runtime-замер (hardware GPU, `?dataset=city`, staging подменён на место
`city-tiles`) упёрся в архитектурный предел: обзор не собрался за 120 с —

полный обзор нельзя собирать из всех детальных тайлов. Нужен отдельно
доставляемый **far-JSON** на те же 437 адресов (упрощённые здания, агрегированная
растительность, обзорный растр земли/дорог, защищённые силуэты landmark'ов) и
объединение обзорных групп ~4 × 4 тайла. Плотность исходных деревьев при этом
не снижается. Переключение рабочего датасета запрещено до прохождения runtime-ворот
(обзор ≤ 1,5 млн треугольников, ≤ 200 draw calls, ≤ 200 МиБ учтённых ресурсов;
близкий вид ≤ 3 млн / ≤ 350 / ≤ 450 МиБ; обзор ≤ 10 с cold).

## Что приложить к review (шаг 0 + шаг 1)

1. [`area.json`](area.json) и [`coverage.svg`](coverage.svg) — область, кольцо,
   кладбище, текущая рамка, сетка.
2. [`BASELINE.json`](BASELINE.json) — baseline текущих датасетов.
3. `scripts/normalize/tests/test_area_contract.py` — протокол проверок контракта.
4. Числа экстракции из таблицы выше (94 999 raw building-feature, 59 с, 98,79 МБ).
5. Diff `geo_config.py` / `extract.py` / `normalize.py` / `trees.py`.

После приёмки: staging-генерация 437 тайлов, проверка покрытия по эталонному
контуру МКАД, первый визуальный review контрольных территорий (шаг 3 плана).

Staging запускается изолированно (никакие рабочие пути не перезаписываются):

```powershell
.\.venv\Scripts\python.exe scripts\ingest\extract.py --area city `
  --out data\interim\city_raw_b2.geojson --trees-out data\interim\city_trees_b2.json
.\.venv\Scripts\python.exe scripts\normalize\normalize.py --area city --profile `
  --raw data\interim\city_raw_b2.geojson --trees-raw data\interim\city_trees_b2.json `
  --tiles-dir public\data\city-tiles-b2 --out data\processed\city_area_b2_normalized.json `
  --coverage-out data\processed\coverage_city_b2.json
.\.venv\Scripts\python.exe scripts\validation\coverage_report.py --area city `
  --tiles-dir public\data\city-tiles-b2 --coverage data\processed\coverage_city_b2.json `
  --report docs\COVERAGE_REPORT_CITY_B2.md
.\.venv\Scripts\python.exe scripts\qa\b2_staging_audit.py `
  --tiles-dir public\data\city-tiles-b2 --coverage data\processed\coverage_city_b2.json
```

На staging обязательно проверить: ровно 437 адресов и совпадение счётчиков
manifest с записанными объектами; `trees_budget_scale = 1` (значение <1 —
глобальное прореживание деревьев, теперь это ошибка пайплайна);
`trees_unassigned = 0`; отсутствие `missing_outer`/пустых relations сверх
объяснённых; тайминги и пиковую память (`--profile`); неизменность внутренних
зон против [`BASELINE.json`](BASELINE.json).

Дополнительно (по ревью Codex):

* до запуска снять GPU/визуальный baseline **текущего** датасета — до этого
  шаг 0 считается неполным;
* сверить baseline-хеши рабочих данных до и после staging: рабочие
  `coverage_city.json` / `city_area_normalized.json` и `public/data/city-tiles`
  не должны измениться;
* `trees_budget_scale` должно быть ровно 1: лимит поднят до 1 200 000, а значение
  <1 пайплайн теперь отвергает сам (обход — `--allow-tree-thinning`); такой
  результат не принимается;
* сравнивать неизменность только внутри одинаковых зон/территорий, а не по
  суммарным итогам 144 и 437 тайлов;
* к пакету ревью приложить реальные команды, exit codes, пиковый RSS и
  объяснение двух `empty` relations из извлечения.
